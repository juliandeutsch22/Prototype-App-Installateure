# Legacy Analysis — Perl Zeiterfassung & Materialbestellung

Authoritative reference for porting the single-file legacy web app
(`c5eeee76-perlinstallateurwebapp.html`, ~10,424 lines) to React/TypeScript.

Stack: single HTML file, Firebase JS SDK v9.15.0 (Firestore + Auth), Tailwind CDN, jsPDF 2.5.1 + jspdf-autotable 3.8.2, Google Fonts (Poppins).
Language: German (Austrian business). Currency EUR, `de-AT`/`de-DE` formatting.

> Field-name accuracy note: collection docs are **schemaless** — different code paths write slightly different field sets. Some legacy/duplicate fields exist (e.g. `weekly_hours` is written as a duplicate of `weeklyTargetHours`). All are listed below.

---

## 1. Firestore Collections

Firestore root collections (all flat, no subcollections): `users`, `projects`, `assignments`, `materials`, `materialOrders`, `timeEntries`, `invoices`.

A Firestore document ID (`doc.id`) is read into a JS property — usually `id`, but in user management it is read as `docId`. The business key that links records is **not** the doc ID:
- `users` link to auth via the **`uid`** field (Firebase Auth UID), NOT the doc ID.
- Everything else links to projects via the string **`projectNumber`** (e.g. `"2024-001"`), NOT a project doc ID.
- timeEntries/materialOrders link to a user via **`userId`** (= the auth `uid`).

## 2. Roles

## 4. Business Logic to Preserve

### 4.1 Austrian holidays & weekend detection

`getAustrianHolidayName(date)` returns the holiday name or `null`. `isAustrianHoliday(date)` = name !== null.

**Fixed holidays** (key `month-day`, month 1-indexed):
- `1-1` Neujahr, `1-6` Heilige Drei Könige, `5-1` Staatsfeiertag, `8-15` Mariä Himmelfahrt, `10-26` Nationalfeiertag, `11-1` Allerheiligen, `12-8` Mariä Empfängnis, `12-25` Christtag, `12-26` Stefanitag.

**Variable (Easter-based)** via `getEasterDate(year)` (Gauss/Butcher algorithm), offsets in days from Easter Sunday:
- `+1` Ostermontag, `+39` Christi Himmelfahrt, `+50` Pfingstmontag, `+60` Fronleichnam.

(Easter Sunday itself and Good Friday are NOT in the list.)

**Weekend** = `date.getDay() === 0 || === 6` (Sun/Sat).

`lastWorkday(fromDate)`: start at `fromDate - 1 day`, then skip back while weekend OR Austrian holiday; returns `'YYYY-MM-DD'` (local).
`localDateStr(d)` builds `YYYY-MM-DD` from local components (avoids UTC offset bug). `todayStr()` = `localDateStr(new Date())`.
`getISOWeek(date)` returns `{week, year}` ISO-8601 calendar week (UTC-based Thursday rule).

### 4.2 Time-entry hours & overtime saldo

`calcWorkMin(entry)`: only for `status === 'Anwesend'` with start+end; `(end − start) in minutes − breakDuration`, floored at 0. (Times parsed as `new Date('1970-01-01T'+HH:MM)`.) `travelTime` is stored but NOT added to worked minutes in this calc.

`fmtMin(m)` → `'HH:MM'`.

`calcOverallSaldo(userData, entries)`:
- Returns `{saldoH, hasConfig, hasOverride}`; **zeroed** for roles where `shouldShowOvertime` is false (GF/Admin).
- `initial = userData.initial_overtime` (hours).
- `weeklyH = userData.weeklyTargetHours ?? 40`; `workDays = userData.work_days ?? [1,2,3,4,5]`.
- Daily target `dailyH = weeklyH / workDays.length`.
- **Ist (actual)** = sum over entries with `date >= app_start_date`:
  - `Anwesend` → `calcWorkMin`-style worked minutes;
  - `Krank` or `Urlaub` → counts as `dailyH * 60` minutes (fulfills target).
- **Soll (target)** = for each calendar day from `app_start_date` through **yesterday** (today excluded), if `getDay() ∈ workDays` AND **not** an Austrian holiday → add `dailyH * 60`. (Holidays = no target, like Sundays.)
- `saldoH = initial + (istMin − sollMin)/60`, rounded to 2 decimals.
- No `app_start_date` → returns just `initial`, `hasConfig=false`.

> **No explicit weekend/holiday pay surcharge (Zuschlag) exists.** Weekends/holidays only affect the target (Soll) side — they reduce required hours, they do NOT multiply earned hours. There is no surcharge multiplier anywhere in the code.

Monthly accounting view computes per-month Soll = workdays (excluding weekends, holidays, Krank/Urlaub days) × daily target, and counts `holidaysInMonth` separately for display.

### 4.3 Material pickup / order status state machine

Order statuses: `Offen → In Bearbeitung → Abholbereit → Erledigt`. Returns are created directly as `Erledigt`.

**Stock handling on `Erledigt`** (atomic, idempotent via `runTransaction` + `processed` flag):
- Two implementations with identical logic — `bindGroupCardEvents` (admin status buttons) and `updateOrderStatus` (shared handler for dashboard/employee).
- On transition to `Erledigt` AND `processed !== true`: transaction reads the order; if already `processed` → just set status; else `materials.stock += increment(-quantity)`, set `status:'Erledigt', processed:true, updatedAt`.
- Any other status change → plain `updateDoc({status, updatedAt})`.

**Returns (Retoure)**: `addDoc` with `transactionType:'return', status:'Erledigt'`. If `condition === 'neu'` → `materials.stock += increment(+quantity)` (back into stock).

**Assignment pickup confirmation** (dashboard, employee confirms picking up scheduled material): adds the material key to `assignments.pickedUpMaterials` for all of that day's assignment docs, and decrements `materials.stock` via transaction `stock = max(0, current − qty)` (skips `free-…` ad-hoc materials). Stock failure is non-critical (warning only).

### 4.4 Assignment / scheduling logic (Einsatzplanung)

- Planner picks **date** + **project** + checks employees (each with an optional "as helper" checkbox) + optional materials list + comment.
- Save = **delete-then-recreate**: `getDocs(where date == X, projectNumber == Y)` → delete all → `addDoc` one `assignments` doc per checked employee (fields per §1.3).
- Employee views own assignments by `where('userId','==',uid)` then filters to the month client-side.
- Delete single assignment by doc ID, or delete a whole (date, projectNumber) group.

### 4.5 Invoice generation (jsPDF + autotable)

Entry: `generateInvoicePDF(projectNumber)`. Defaults: `INVOICE_RATES_DEFAULT = { fach: 65, helper: 45, lehrling: 35 }` (€/h), VAT `0.20` (20%), material markup `15%`, due days `14`. All overridable via modal inputs.

**Position assembly** (`normProjNr` normalizes the project number for matching):
- Eligible time entries: `status === 'Anwesend'`, matching projectNumber, `!isBilled`. Split worked minutes into `fachMin` (isHelper=false) and `helperMin` (isHelper=true).
- `fachH = fachMin/60`, `helperH = helperMin/60`.
- Eligible material orders: matching projectNumber, `transactionType !== 'return'`, `status === 'Erledigt'`, `!isBilled`. `matNetto += purchasePrice × (1 + markup) × quantity`.
- Positions: Facharbeiterstunden (qty=fachH, up=rates.fach), Helferstunden (qty=helperH, up=rates.helper), Material lump sum (qty=1, "pauschal"), plus any manual items (`invManualItems`, unit "Stk.").

**Totals**: `nettoTotal = Σ net`; `vatAmt = nettoTotal × vatRate`; `bruttoTotal = nettoTotal + vatAmt` (saved 2-decimal).

**PDF layout** (A4 portrait, mm, margin 18):
- Letterhead: logo (top-right, from `assets/Logo_neu_2021.png`), "Perl Installationen GmbH", address line, contact line, blue rule. Hardcoded company data: Musterstraße 1 · 1010 Wien · IBAN `AT12 3456 7890 1234 5678` · BIC `RLNWATWW` · Bank Austria · UID `ATU12345678` · FN 123456a.
- Recipient = project customerName + address; right block = Rechnungsnummer / Rechnungsdatum / Zahlungsziel.
- `autoTable`: head `['Position','Menge','Einheit','EP €','Netto €']`, foot rows Netto / `USt. X%` / Brutto. Header fill blue `[0,51,102]`.
- Payment instruction line + Verwendungszweck `invoiceNumber / projectNumber`. Footer with legal info.
- **Optional page 2 "Leistungsnachweis"** (if `appendDetail` and entries exist): per-entry table `['Datum','Mitarbeiter','Typ','Tätigkeit / Notiz','Std.']` (Typ = Helfer/Fachkraft, notiz truncated to 60 chars), sorted by date.
- `doc.save('${invoiceNumber}.pdf')`.

**Post-generate side effects**: set `isBilled:true, invoiceNumber` on all linked timeEntries + materialOrders (Promise.all); `addDoc` the invoice doc; `syncNextInvoiceNumber`.

### 4.6 Invoice numbering & status lifecycle

- `getSuggestedInvoiceNumber()` → `RE-${currentYear}-${pad4(invNextNumber)}`; `invNextNumber` starts at `1001`.
- `invNextNumber` is **derived from Firestore** in the invoices `onSnapshot`: `max(parsed trailing number across all invoices) + 1`.
- `syncNextInvoiceNumber(used)` bumps `invNextNumber` to `n+1` if the manually-used number ≥ current.
- Duplicate check before generating: warns (confirm) if a non-Storniert invoice already has that number. No `runTransaction` for numbering — it is **not collision-safe** under concurrency.
- **Mahnwesen (auto-overdue)**: in `renderInvoiceList`, any `Offen` invoice with `dueDate < today` is flipped to `Überfällig` via `updateDoc` (guarded by in-memory `_overdueMarked`).
- **Status changes**: manual buttons set `paymentStatus` (`Bezahlt`, etc.) with `updatedAt`.
- **Cancel (Storno)** `cancelInvoice`: sets invoice `paymentStatus:'Storniert', cancellationNote, cancelledAt`; releases linked entries/orders (`isBilled:false, invoiceNumber:''`). Firestore can't delete a field via updateDoc, so `invoiceNumber` is set to `''`.
- **Reactivate**: re-marks linked entries/orders `isBilled:true` + invoiceNumber, sets invoice `paymentStatus:'Offen', cancelledAt:null, cancellationNote:null`.
- **Delete**: only allowed when `paymentStatus === 'Storniert'`.

### 4.7 `runTransaction` usage summary

1. `bindGroupCardEvents` order → `Erledigt`: atomic stock decrement + `processed` guard.
2. `updateOrderStatus` (shared) order → `Erledigt`: same.
3. Dashboard assignment material pickup: `stock = max(0, current − qty)`.

No transactions on invoice numbering, user creation, or assignment save (those use plain add/delete/update).

## 6. Secondary-app pattern (~line 7955)

In user management create flow, to **create a new auth user without logging out the current admin**:

```js
const secAppName = 'secondary_' + Date.now();          // unique name each time
const secApp  = initializeApp(firebaseConfig, secAppName);
const secAuth = getAuth(secApp);
const cred = await createUserWithEmailAndPassword(secAuth, email, pw);
const newUid = cred.user.uid;
await signOut(secAuth);                                  // sign out only the secondary
// then addDoc to 'users' with uid:newUid, then sendPasswordResetEmail(auth, email)
```

A fresh named secondary app is created **every time** (timestamped name) so `getApps()` caching can't return a stale instance / wrong UID. `createUserWithEmailAndPassword` on the **secondary** auth keeps the **primary** auth session (the admin) untouched. After creating the Firestore user doc, a password-reset/welcome email is sent so the new user sets their own password. The temporary password (`generatePassword()` / manual) is only used to create the account.

## 7. Auth flow

1. `login-form` submit: choose persistence — `browserLocalPersistence` if "remember me" checked, else `browserSessionPersistence` → `setPersistence(auth, …)` → `signInWithEmailAndPassword(auth, email, pw)`. Generic German error on failure.
2. Password reset: `sendPasswordResetEmail(auth, email)` from the forgot-password modal.
3. `onAuthStateChanged(auth, …)`:
   - Tears down all listeners + resets all module-level state on every change.
   - If a user is present: **role lookup** `getDocs(query(collection(db,'users'), where('uid','==',firebaseUser.uid)))`.
     - If `snap.empty` → `signOut(auth)` (no Firestore user = not allowed in).
     - Else `currentUser = { uid: firebaseUser.uid, ...snap.docs[0].data() }`; fills header name/role; hides login, shows app; `buildNav(currentUser)`.
   - If no user → show login screen.
4. `buildNav(user)` caches `currentUserRoleGlobal` and `window._dashUser`, shows crown for Admin, conditionally adds nav tabs + initializes each view per the role predicates (§2/§3), builds mobile bottom-nav, then `showView('view-dashboard')`.
5. Logout: `signOut(auth)` from header buttons.

> Authorization is **client-side only** in this legacy app (UI gating by role). A real backend/Firestore Security Rules layer must enforce these rules server-side when porting.
